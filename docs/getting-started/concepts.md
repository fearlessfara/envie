# Core Concepts

Understanding these core concepts will help you use Envie effectively.

## Overview

Envie helps you manage **multiple ephemeral environments** in Terraform with:
- Layered dependencies
- Flexible resource sharing
- Automatic state management

## Key Concepts

### 1. Environments

Environments represent different deployment contexts for your infrastructure.

#### Ephemeral Environments

Temporary environments for development and testing:

```yaml
ephemeral:
  naming_pattern: "{project}-{id}"
  # Examples: myapp-dev-123, myapp-feature-auth
```

**Use cases**:
- Feature branch testing
- MR/PR previews
- Integration testing
- Developer sandboxes

**Characteristics**:
- Created on-demand
- Short-lived
- Isolated from each other
- Easy to destroy

#### Stable Environments

Long-lived environments for shared infrastructure:

```yaml
stable:
  sandbox:
    workspace: myapp-sandbox
  production:
    workspace: myapp-production
```

**Use cases**:
- Shared development database
- Staging environment
- Production infrastructure

**Characteristics**:
- Pre-defined
- Long-lived
- Shared across teams
- Protected from accidental changes

### 2. Units

Units are deployable pieces of infrastructure defined by `envie.yaml` files.

```yaml
name: api
description: API Lambda functions
unit_type: component
state_management: dedicated

depends:
  - path: ../database
    environment: stable.sandbox
  - path: ../networking
    environment: ephemeral
```

#### Unit Types

- **Component**: Basic building block (Lambda, API Gateway, etc.)
- **Service**: Collection of related components
- **Module**: Reusable infrastructure pattern
- **Layer**: Foundational infrastructure

#### State Management

How Terraform state is managed:

- **Dedicated**: Each unit has its own state file
  ```yaml
  state_management: dedicated
  ```

- **Parent**: Shares state with parent unit
  ```yaml
  state_management: parent
  ```

- **Shared**: Shares state with named group
  ```yaml
  state_management: shared
  ```

### 3. Dependencies

Dependencies define relationships between units.

```yaml
depends:
  - path: ../../database/dynamodb
    environment: stable.sandbox
  - path: ../../networking/vpc
    environment: ephemeral
```

**Key points**:
- Envie automatically determines deployment order
- Dependencies can use different environments (mix stable and ephemeral)
- Auto-generates `terraform_remote_state` data sources

### 4. Environment Resolution

How Envie determines which environment each dependency uses:

#### Default (from envie.yaml)

```yaml
depends:
  - path: ../database
    environment: stable.sandbox  # ← Default
```

#### CLI Override (using -E flag)

```bash
envie deploy --unit api --env dev-123 \
  -E database:stable.production  # ← Override
```

**Priority**: CLI override > envie.yaml default

### 5. Workspaces

Terraform workspaces isolate state for different environments.

```yaml
ephemeral:
  naming_pattern: "{project}-{id}"
  # Creates workspace: myapp-dev-123

stable:
  production:
    workspace: myapp-production
    # Uses workspace: myapp-production
```

**Auto-generated by Envie**:
- Ephemeral: `{project}-{env-id}`
- Stable: Explicitly defined in config

### 6. Remote State

Envie automatically generates remote state data sources.

#### Generated File: `envie-remote-state.tf`

```hcl
data "terraform_remote_state" "database_dynamodb" {
  backend = "s3"
  workspace = "myapp-sandbox"

  config = {
    bucket = "myapp-terraform-state"
    key = "stable/sandbox/database/dynamodb/terraform.tfstate"
  }
}
```

#### Usage in Your Terraform

```hcl
resource "aws_lambda_function" "main" {
  environment {
    variables = {
      TABLE_NAME = data.terraform_remote_state.database_dynamodb.outputs.table_name
    }
  }
}
```

### 7. Backend Configuration

S3 backend for Terraform state storage.

#### Generated File: `envie-backend.tf`

```hcl
terraform {
  backend "s3" {
    bucket = "myapp-terraform-state"
    key = "ephemeral/myapp-dev-123/api/terraform.tfstate"
    workspace = "myapp-dev-123"
    dynamodb_table = "myapp-terraform-locks"
  }
}
```

**Auto-created by Envie**:
- S3 bucket for state files
- DynamoDB table for state locking
- Versioning enabled
- Encryption at rest

## Visual Example

### Project Structure

```
myapp/
├── workspace.envie.yaml          # Global config
└── services/
    ├── networking/
    │   └── envie.yaml             # Unit: networking
    ├── database/
    │   └── envie.yaml             # Unit: database
    └── api/
        └── envie.yaml             # Unit: api (depends on database, networking)
```

### Deployment Flow

```
1. User runs: envie deploy --unit api --env dev-123

2. Envie discovers:
   - api depends on database + networking
   - database uses stable.sandbox
   - networking uses ephemeral

3. Envie resolves:
   - api → workspace: myapp-dev-123
   - database → workspace: myapp-sandbox
   - networking → workspace: myapp-dev-123

4. Envie deploys in order:
   1. networking (no dependencies)
   2. database (no dependencies)
   3. api (depends on both)

5. Envie generates for each:
   - envie-backend.tf (backend config)
   - envie-remote-state.tf (data sources)

6. Terraform applies changes
```

## Common Patterns

### Pattern 1: Full Isolation

All resources in ephemeral environment:

```yaml
depends:
  - path: ../database
    environment: ephemeral
  - path: ../networking
    environment: ephemeral
```

**Use case**: Complete integration testing

### Pattern 2: Partial Sharing

Mix ephemeral and stable:

```yaml
depends:
  - path: ../database
    environment: stable.sandbox  # ← Shared
  - path: ../networking
    environment: ephemeral        # ← Isolated
```

**Use case**: Testing API changes with stable data

### Pattern 3: Production Testing

Test against production (read-only!):

```yaml
depends:
  - path: ../database
    environment: stable.production  # ← Production
  - path: ../networking
    environment: ephemeral            # ← Isolated network
```

**Use case**: Performance testing with real data

## Best Practices

1. **Use descriptive environment IDs**
   - ✅ `feature-auth`, `mr-123`, `dev-alice`
   - ❌ `test`, `temp`, `x`

2. **Set appropriate defaults in envie.yaml**
   - Use stable for slow/expensive resources (databases)
   - Use ephemeral for fast/cheap resources (Lambda)

3. **Clean up ephemeral environments**
   ```bash
   envie delete --env old-feature  # Complete cleanup
   ```

4. **Use dry-run before deploying**
   ```bash
   envie plan --unit api --env test
   ```

5. **Add descriptions to all units**
   ```yaml
   name: api
   description: API Lambda functions and endpoints
   ```
