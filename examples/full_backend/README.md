# Full Backend Example - Envie Multi-Unit Deployment

This example demonstrates a complete serverless backend using Envie to orchestrate multiple Terraform units with cross-unit dependencies.

## Architecture

```
┌─────────────────────────────────────────────────────────────┐
│                      full_backend                            │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  ┌──────────┐      ┌──────────┐      ┌──────────┐          │
│  │   core   │      │    db    │      │   api    │          │
│  │          │      │          │      │          │          │
│  │ API GW   │◄─────┤ DynamoDB │◄─────┤  Lambda  │          │
│  │  Base    │      │          │      │   CRUD   │          │
│  └──────────┘      └──────────┘      └──────────┘          │
│                                           │                  │
│                                           │                  │
│                     Dependencies:         │                  │
│                     api → core (API GW)   │                  │
│                     api → db (DynamoDB)   │                  │
└─────────────────────────────────────────────────────────────┘
```

## Units

### 1. **core** - API Gateway Foundation
- Creates AWS API Gateway REST API
- Provides base resources and deployment
- **Outputs**: api_id, api_root_resource_id, api_execution_arn, api_invoke_url
- **Dependencies**: None

### 2. **db** - DynamoDB Database
- Creates DynamoDB table using [terraform-aws-modules/dynamodb-table](https://registry.terraform.io/modules/terraform-aws-modules/dynamodb-table/aws)
- Configures: Pay-per-request billing, point-in-time recovery, TTL
- **Outputs**: table_name, table_arn
- **Dependencies**: None

### 3. **api** - Lambda API Endpoints
- Creates Lambda function using [terraform-aws-modules/lambda](https://registry.terraform.io/modules/terraform-aws-modules/lambda/aws)
- Configures API Gateway endpoints: `/items` (GET, POST), `/items/{id}` (GET, PUT, DELETE)
- **Dependencies**:
  - `core` (uses API Gateway ID and resources)
  - `db` (uses DynamoDB table name and ARN)

## How Envie Works Here

### Cross-Unit Dependencies

The `api` unit's `envie.yaml` declares dependencies:

```yaml
depends:
  - path: ../core
    environment: ephemeral
  - path: ../db
    environment: ephemeral
```

When you deploy the `api` unit, **Envie automatically generates** `remote_state.envie.tf`:

```hcl
# Auto-generated by Envie - DO NOT EDIT

data "terraform_remote_state" "core" {
  backend   = "s3"
  workspace = "full-backend-dev123"
  config = {
    bucket = "full-backend-terraform-state"
    key    = "core/terraform.tfstate"
    region = "us-east-1"
  }
}

data "terraform_remote_state" "db" {
  backend   = "s3"
  workspace = "full-backend-dev123"
  config = {
    bucket = "full-backend-terraform-state"
    key    = "db/terraform.tfstate"
    region = "us-east-1"
  }
}
```

Then in `main.tf`, you simply reference:

```hcl
locals {
  api_id     = data.terraform_remote_state.core.outputs.api_id
  table_name = data.terraform_remote_state.db.outputs.table_name
}
```

**No manual remote state configuration needed!** Envie handles it all.

## Prerequisites

1. **AWS Account** with credentials configured
2. **Envie** built from source:
   ```bash
   cd ../../  # Go to envie root
   cargo build --release
   # Binary will be at: target/release/envie
   ```
3. **Terraform** >= 1.0
4. **AWS CLI** configured
5. **S3 Bucket** for Terraform state: `full-backend-terraform-state`
6. **DynamoDB Table** for state locking: `full-backend-terraform-locks`

### Create State Backend (One-time setup)

```bash
# Create S3 bucket for state
aws s3 mb s3://full-backend-terraform-state --region us-east-1

# Enable versioning
aws s3api put-bucket-versioning \
  --bucket full-backend-terraform-state \
  --versioning-configuration Status=Enabled

# Create DynamoDB table for locks
aws dynamodb create-table \
  --table-name full-backend-terraform-locks \
  --attribute-definitions AttributeName=LockID,AttributeType=S \
  --key-schema AttributeName=LockID,KeyType=HASH \
  --billing-mode PAY_PER_REQUEST \
  --region us-east-1
```

## Deployment Guide

### Quick Start (Using Deploy Script)

```bash
# Navigate to example directory
cd examples/full_backend

# Deploy everything to environment 'dev123'
./deploy.sh dev123

# Destroy everything
./deploy.sh dev123 --destroy
```

### Manual Deployment (Step-by-Step)

```bash
# Navigate to project root
cd examples/full_backend

# Set envie path (from project root)
ENVIE=../../target/release/envie

# Deploy all units in correct order for environment 'dev123'
# Envie automatically resolves dependencies and deploys in order: core → db → api

# Deploy core unit (API Gateway)
$ENVIE deploy --unit core --env dev123

# Deploy db unit (DynamoDB)
$ENVIE deploy --unit db --env dev123

# Deploy api unit (Lambda + Endpoints)
# This will automatically read outputs from core and db!
$ENVIE deploy --unit api --env dev123
```

### Dry Run (See What Will Happen)

```bash
# See deployment plan without making changes
$ENVIE deploy --unit api --env dev123 --dry-run
```

### Deploy to Different Environments

```bash
# Development
$ENVIE deploy --unit api --env dev

# Feature branch
$ENVIE deploy --unit api --env feature-auth

# Production (using stable environment)
$ENVIE deploy --unit api --env staging
```

### Cross-Environment Dependencies

You can even have units depend on different environments!

For example, if you want your `api` to use production database:

```bash
# Deploy api to dev, but use production database
$ENVIE deploy --unit api --env dev123 --environment db:stable.prod
```

This tells Envie: "Deploy api to dev123, but read the DynamoDB table from the production environment"

## Testing the API

After deployment, get the API URL from outputs:

```bash
# Get the API invoke URL
cd units/api
terraform output api_endpoints
```

### Create an Item

```bash
API_URL="https://xxxxx.execute-api.us-east-1.amazonaws.com/dev123"

curl -X POST "$API_URL/items" \
  -H "Content-Type: application/json" \
  -d '{"name": "Test Item", "description": "My first item"}'
```

### List All Items

```bash
curl -X GET "$API_URL/items"
```

### Get Specific Item

```bash
curl -X GET "$API_URL/items/{id}"
```

### Update Item

```bash
curl -X PUT "$API_URL/items/{id}" \
  -H "Content-Type: application/json" \
  -d '{"name": "Updated Item", "description": "Updated description"}'
```

### Delete Item

```bash
curl -X DELETE "$API_URL/items/{id}"
```

## Cleanup

```bash
# Using the script
./deploy.sh dev123 --destroy

# Or manually in reverse order (important!)
$ENVIE destroy --unit api --env dev123
$ENVIE destroy --unit db --env dev123
$ENVIE destroy --unit core --env dev123

# Or destroy everything at once
$ENVIE delete --env dev123
```

## Project Structure

```
full_backend/
├── workspace.envie.yaml         # Global project configuration
├── README.md                    # This file
└── units/
    ├── core/                    # API Gateway base
    │   ├── envie.yaml          # Unit configuration
    │   └── main.tf             # Terraform code
    ├── db/                      # DynamoDB table
    │   ├── envie.yaml
    │   └── main.tf
    └── api/                     # Lambda + API endpoints
        ├── envie.yaml          # Declares dependencies on core & db
        ├── main.tf             # Uses remote state from core & db
        └── lambda/
            ├── index.js        # Lambda handler (CRUD operations)
            └── package.json    # Dependencies
```

## Generated Files (Gitignored)

When you deploy, Envie generates these files in each unit:

- **`backend.envie.tf`** - Backend configuration for this unit's state
- **`remote_state.envie.tf`** - Data sources for dependency outputs
- **`locals.envie.tf`** - Project metadata (name, environment, tags)

These are automatically managed by Envie and should be in `.gitignore` (pattern: `*.envie.tf`).

## Key Takeaways

1. **Each unit is independent** - Can be deployed/destroyed separately
2. **Envie manages dependencies** - Automatically generates remote state configuration
3. **Cross-state references** - Units can depend on outputs from any other unit
4. **Environment flexibility** - Mix and match environments per dependency
5. **No manual plumbing** - Envie handles all the Terraform remote state boilerplate
